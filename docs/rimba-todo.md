  - ⛔ **DO NOT STAGE S1→S4 YET — the break-even is not computable, and RAW is not the binding constraint today.** Analysis 2026-07-31, worklog [`break-even`](worklog/2026-07-31-raw-breakeven-model.md). Four independent gaps sink the calculation: (1) **the ~22 % is a LINUX-AP number** — the throughput A/B was chronite→chronium with **zero ESP boards**, and no ESP throughput A/B exists; (2) the cost is transport-dependent and unresolved — TCP says −22 %, UDP at fixed offered rate says **−7.1 pp**, and TCP is reactive, so the *airtime* cost is likely nearer 7 %; (3) **one RAW config was ever measured** (2 of a possible 6 slots, 19.7 % window, `cross_slot=0` never varied) — it was chosen to be byte-diffable, **not** to be good, so 22 % is the cost of a deliberately weak schedule; (4) **the benefit has never been observed at all** — the bench maxes out at ~3 contending nodes. An attempt to settle the mechanism by measurement failed honestly: `ping -i 0.002` achieved **~4 pps = ~1 % of link capacity**, so the resulting 5 % deferral ratio measures the load, not the mechanism, and a saturating downlink against the ESP AP is unobtainable (no iperf server in the fixture). **THE PLAN CHANGE:** the gate's ceiling is **8 clients today** and proxy-ARP binds at ~30 — RAW fixes only the third blocker (EDCA), so **raise the ceiling first** (the tracked easy+medium tiers, next item); until then no RAW benefit is observable *in principle*. Then run the missing ESP-AP A/B swept over window fraction, slot count and `cross_slot=1` at increasing client counts. **Gap 5, found last and decisive alone: the contention model has no clock** — `aSlotTime` and SIFS do not exist as microsecond values in ANY of the four trees (only `SHORT_SLOT_TIME` capability bits, plus hostapd's own placeholder `wmm.c:253` `50 /* FIX: proper SIFS + ACK duration */`); they live in the blob, so any model must *assume* the constants that then decide its answer. ⚠⚠ **AND COST AND BENEFIT FALL ON OPPOSITE SIDES OF THE LINK.** EDCA is deliberately asymmetric: the AP advertises AC_BE **CWmax 1023** to its STAs but uses **63** itself (`ap_config.c:211-222` vs `:223-231`), so under load the STAs back off 16× further while the AP keeps winning — **contention degrades STA UPLINK, while the measured ~22 % cost is AP DOWNLINK.** The AP is already partly self-protecting against the problem RAW is being ported to fix. ⚠ **So the cheapest and highest-value open question is: characterise the expected traffic mix.** Downlink-heavy ⇒ RAW pays a real cost to fix a problem the AP is insulated from; uplink-heavy (the archetypal HaLow sensor gate) ⇒ the cost is far smaller than these downlink-only numbers imply and the benefit lands where the pain is. Needs no hardware, no bench slot, no firmware — and it plausibly decides the feature. (Also: the ESP AP is *configured to contend differently* from the Linux AP the 22 % came from — morselib AC_BE CWmax **1023** / TXOP **15008 µs** vs the Linux AP's **63** / **0**, `umac_config.c:13-51`.)
- ☐ **Decision:** choose the L2 after the comparison (or define when each applies). Trade-off table in both milestone docs.
