# 2026-07-30 — RAW S0b-2: the gate is passed. The chip's RAW engine arms, and a STA obeys it

**Goal.** Answer the one question the entire AP-side RAW port has been gated on since the 2026-07-24
recon: **does the MM6108 firmware actually act on a RAW schedule authored by the host?** The scoping pass
established this is decidable on Linux hardware alone — the blob is the same file on both platforms and
RAW reaches the chip only as beacon bytes — so a negative here would BLOCK the port with no ESP code
written.

**Outcome. ✅ Q3a PASS, Q4 PASS.** The engine arms from a host-authored beacon, gates the AP's own TX, and
a STA parses a *received* RPS and self-restricts. The golden byte constant was validated on air,
byte-identical, in every beacon. **The feature is no longer gated on a source-undecidable firmware
question** — what remains is entirely ESP-host-side.

One measurement had to be **voided**, and the reason is a finding in its own right: data-frame capture
loss is **66 %**, versus the 2.5 % beacon loss S0b-1 measured.

**Nothing was committed. Bench returned to radio silence on all three nodes.**

## 1. Rig

| | |
|---|---|
| **chronite** | AP. `hostapd_s1g` from the tracked `hostapd-rimba.conf`, then RAW driven **directly by `morse_cli`** — not hostapd's `raw={}` block, which would have applied its own defaults |
| **chronogen** | STA. `wpa_supplicant_s1g`, SSID `rimba-ping`, **`raw_sta_priority=0`**. Associated in 10 s at **AID 1** |
| **chronium** | monitor on `morse0`, S1G ch27 |
| **chronosalt** | deliberately unused — documented as browning out on radio-up |
| ESP boards | **none** |

RSSI −53 dBm (STA→AP) / −57 dBm (AP→STA) — nowhere near the ≈−3 dBm overload signature.

The RAW config, pinned explicitly per the S0b-0 finding that hostapd's defaults emit a different element:

```
morse_cli -i wlan1 raw -s 20200,2 -a 1,255 -t 0 enable 1
morse_cli -i wlan1 raw enable 0
```

Driver readback (passive debugfs `dump_raw_configs`) confirmed it landed exactly as intended:

```
RAW ID: 1 (enabled: 1)
  start_time_us=0  aid: start=1 end=255
  slot info: x-slot=0 num=2 duration_us=10100
```

`duration_us=10100` is the 20200 total divided by 2 slots — the double-truncation behaviour S0b-0
predicted from source, landing exactly on the golden parameter.

`morse_cli raw --help` also confirmed the two things the analysis method depends on: `-s` is the **total**
RAW duration, and `-t` is *"Start time for the RAW window **from the end of the frame**"* — the
beacon-end reference, not TBTT.

## 2. Negative control, then the element on air

**Negative control (free, from S0b-1's capture):** with RAW **disabled**, all 2222 beacons carried the
IE set `{0, 5, 213, 214, 217, 221, 232}` and **zero** EID-208 elements. So anything at 208 afterwards is
attributable to the RAW config, not to something the firmware emits regardless.

With RAW enabled, 236 S1G beacons captured, **all 236 parsed cleanly** (IE chain landing exactly on the
end-FCS), and:

```
IE chain (1 distinct, x236) : [213, 5, 208, 217, 232, 214, 0, 221]
EID-208 element (1 distinct): D0 06 20 40 09 04 E0 1F
golden constant (§7.1)      : D0 06 20 40 09 04 E0 1F
BYTE-IDENTICAL              : True
```

**The golden constant is validated on air**, closing the last S0b-0 caveat ("re-derived arithmetically
from source, not observed on air"). The RPS sits at **position 3, directly after the TIM**, matching
Linux's S1G long-beacon ordering table.

A note on method, because I got it wrong first: my initial parser brute-forced the IE start offset and
required the chain to land on the frame end. It matched only 3 of 242 frames and reported *varying*
offsets (10/11/12/13) — which looked like the conditional S1G presence bits (NEXT_TBTT / COMPRESS_SSID /
ANO) being in play, the exact trap the plan flagged. **Both were artefacts:** the frames carry a 4-byte
trailing FCS, and once that is accounted for and the walk is anchored on EID 213, **all 236 frames parse
with a constant 15-byte offset**. The presence bits were *not* set. Worth recording because a
brute-forced offset is exactly how a false "RPS stripped" verdict gets manufactured.

## 3. The gate — counters, both ends

Counters reset to zero on both nodes, then a driven uplink load, then read:

| | AP (chronite) | STA (chronogen) | baseline |
|---|---|---|---|
| `assignments[0]` | **2179** | **2083** | 0 |
| `assignments_truncated_from_tbtt` | 0 | 0 | 0 |
| `invalid_assignments` | **0** | **0** | 0 |
| `already_past_assignment` | 0 | 0 | 0 |
| `aci_frames_delayed` | **92** | **239** | 0 |
| `bc_mc_frames_delayed` | 0 | 0 | 0 |
| `frame_crosses_slot` | **27** | **27** | 0 |

**Q3a — PASS.** `assignments[0]` climbing at roughly one per beacon proves the chip **parses the RPS out
of its own outgoing beacon** every TBTT and registers the assignment. `invalid_assignments = 0` is the
direct confirmation that the bytes are *accepted*, not rejected — the signal that would have caught the
EID-66 error had it shipped. And `aci_frames_delayed` / `frame_crosses_slot` moving proves the chip is
**actively gating its own transmissions** against the window, not merely parsing it.

**Q4 — PASS.** The STA's *own* `assignments[]` climbed to 2083, so it parses a **received** RPS; and its
own `aci_frames_delayed = 239` proves it **defers its own uplink** to obey the window. Since neither host
stack contains an RPS parser (Linux's `raw.c` is AP-only), that behaviour is necessarily in the blob —
and it is the same blob the ESP runs.

An intermediate read is worth recording: with RAW enabled and beaconing but **before any STA associated**,
the AP already showed `Valid: 1516, Invalid: 0` with all `Delayed` counters at zero. The engine arms on
the advertisement alone; the deferral counters only move once there is traffic to defer. That separation
is a useful diagnostic for later stages.

## 4. The timing arm was voided — and why that matters

The phase histogram, computed with the S0b-1 method (relative to the *observed* beacon, never a fitted
grid), put only **9.2 %** of uplink frames inside the advertised `[0, 20200] µs` window — against
**19.7 %** expected if the frames were uniform over the beacon interval. Read naively that says *worse
than no confinement*.

**It is not admissible.** Reconciling against the transmitter's own counters:

| | |
|---|---|
| STA netdev TX packets | **1194** |
| STA MAC-level TX frames | **1681** |
| uplink data frames in the capture | **403** |
| **capture completeness** | **~34 % — i.e. 66 % loss** |

The parse itself was sound: tshark independently found exactly 403 frames carrying the STA's TA, matching
my parser. The capture is simply missing two-thirds of the traffic. Per the confound matrix's row (g) the
run is **voided, and no confinement conclusion may be drawn in either direction.**

**This is the finding.** S0b-1 measured **2.5 %** beacon loss and explicitly flagged, as an untested
caveat, that data frames might be lost at a different rate. They are — at **66 %**, a **26× difference**.
So **S0b-1's calibration does not transfer to data frames**, and any future timing measurement must
reconcile *data-frame* counts against the transmitter's TX counters *before* a phase histogram is
computed. Beacon-count reconciliation is not sufficient. This is now written into the design doc.

It does not weaken the verdict. The counters were designated the primary instrument precisely because
they are immune to capture loss, and they are unambiguous.

## 5. Two things worth carrying forward

- **`frame_crosses_slot = 27` on both ends** — real frames are **too long for a 10100 µs slot** at 1 MHz.
  Combined with the ≤6-slot cap S0b-0 found, this constrains any real RAW schedule: you get at most 6
  slots, and a slot has to be long enough to hold a frame at the operating MCS or the frame is deferred
  rather than fitted. Worth pairing with the mesh-gate contention arithmetic.
- **The AP defers its own downlink too** (`aci_frames_delayed = 92`). For the mesh-gate use case, where
  the gate is already the throughput bottleneck, RAW is not free. The throughput A/B the plan lists as
  "nearly free alongside the counter run" is now clearly worth doing before committing to the port.

## 6. Verification status

- **On hardware, on air, three radios.** All measurements are from live firmware counters and a live
  capture.
- **On-air frame verification: gold standard reached for the RPS element.** The element was captured on
  chronium's `morse0` from a **live Linux device** and byte-diffed against the derived constant —
  236/236 byte-identical, with a negative control from the RAW-disabled baseline. This is the
  *reference-side* frame; the **ESP's** own RPS remains unverified and that obligation is still owed at
  S0b-4.
- **Bench returned to radio silence** — RAW config disabled + deleted, `hostapd_s1g` and
  `wpa_supplicant_s1g` killed, addresses flushed, `morse0` and `wlan1` down, `wlan1` back to `type
  managed` on all three nodes. Verified with `ps -eo comm=` rather than `pgrep -f`, which self-matches.
- No ESP board was involved, so none needed reflashing.

## 7. Caveats

- **This says nothing about the ESP host path.** Q2 (does a host-appended RPS survive the ESP FW's
  legacy→S1G beacon re-conversion?) and Q3b (does the engine arm when the *ESP* is the AP?) are untouched
  and need ESP code.
- **Confinement is not demonstrated, only deferral.** The counters prove frames *were delayed because of
  RAW*; they do not prove the resulting transmissions land inside the window. The measurement that would
  show that was voided (§4). This distinction matters and should not be glossed: the mechanism engages,
  but its on-air effect is not yet characterised.
- **One STA, one AID, one assignment, one session.** The A/B-1 two-STA disjoint-slot design — the
  internally-controlled experiment the plan calls the discriminating one — was not run.
- The AP-side `aci_frames_delayed = 92` is small relative to the STA's 239; not investigated.
- Load was a `ping` flood, not a rate-controlled generator (neither Pi Zero has `iperf3`), and it
  saturated the link, so the offered rate is not precisely known.
