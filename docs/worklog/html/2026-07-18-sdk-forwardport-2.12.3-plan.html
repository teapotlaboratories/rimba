1 · Goal & locked decisions

  • Staged 2.10.4 → 2.11.2 → 2.12.3, compile-verified and tagged at each hop (-esp32-1).
  • Tag style -esp32-N (e.g. 2.12.3-esp32-1) — honest about “upstream + our patches”.
  • Ongoing tracking — keep the mm remote (MorseMicro/mm-iot-sdk) + this repeatable procedure.
  • Mechanics: Option B — 3-way diff-apply onto our tree, 095b1290 (2.10.4) as the near-exact base.

Work branch feat/sdk-forward-port-2.12.3 (off submodule main @ 3c8ded0d). Branch + PR + review before merge; re-run the full regression suite after; bench radio-silent after tests.

2 · Layout & the SCOPE decision (critical)

Our ESP build compiles the SDK from source at components/mm-iot-sdk/framework/… via explicit source lists in each ESP-component CMakeLists.txt:

ESP componentupstream source root it compiles
morselibframework/morselib
hostapframework/src/hostap
mmpktmemframework/src/mmpktmem
mmutilsframework/src/mmutils
regdbframework/src/mmregdb
(morselib build tooling)framework/tools/{metadata/protected_syms.txt, buildsystem/librarymangler.py}
shimsESP-local (components/shims/) — no upstream source

⚠ The full upstream diff is mostly irrelevant to us

Hop 1 touches ~4058 files, but 1259 are doc/html, 832 freertos-libs, 690 aws, 461 bsps, plus STM32 platforms, mbedtls, mmagic, examples — none of which our ESP build compiles or can compile-verify. So the forward-port is scoped to the compiled roots; uncompiled vendored dirs stay at 2.10.4 (dead weight, harmless). Consistent with the -esp32-N tag choice. The alternative — a full 2.12.3 mirror of the entire vendored tree — pulls in thousands of unverifiable changes for zero ESP benefit. Owner to confirm: compiled-scope (recommended) vs full-tree mirror.

3 · Two crucial corrections from the analysis

🐛 Do not trust the old memory verbatim

  1. All hard breaking changes are in HOP 1 (2.10.4→2.11.2), not spread across hops. Adversarially verified: at 2.11.2 the datapath STA/AP split, umac_interface_add(datapath_ops,…), morse_cmd_tx(…,skip_errlog) and the reshaped umac_datapath_ops struct are already in place and unchanged at 2.12.3. Hop 2 is almost entirely additive (relay subsystem, DPP QR-code).
  2. construct_80211_data_header and frames_allowed_pre_association are RETAINED (memory said dropped). umac_interface_type_is_compatible_with_active does not exist at either endpoint.

4 · Conflict surface (git ground-truth, scoped to compiled roots)

  • Hop 1: 402 upstream file changes → 31 conflicts (30 morselib, 1 hostap/wpa_supplicant/ap.c). protected_syms.txt is conflict-free (upstream didn't touch it).
  • Hop 2: 44 upstream file changes → 11 conflicts (10 morselib, 1 hostap/hostap_morse_common.h).

⚠ The main bench risk

The 268-file hostap (wpa_supplicant) update in hop 1 applies to us but overlaps our edits on only ap.c. Our mesh SAE/AMPE security integrates with hostap, and compile-verify cannot vet the semantic interaction — the regression suite must.

5 · Mechanics (per hop)

# one-time: real upstream remote (done)
git remote add mm git@github.com:MorseMicro/mm-iot-sdk.git ; git fetch mm --tags
ROOTS="framework/morselib framework/src/hostap framework/src/mmpktmem framework/src/mmutils framework/src/mmregdb framework/tools"
# hop1 (095b1290->b61d4548); hop2 (b61d4548->88606f94):
git -C components/halow diff <from> <to> -- $ROOTS | git -C components/halow apply --3way --directory=components/mm-iot-sdk
# then, MANUALLY (git apply won't): sync each ESP component CMakeLists.txt SRCS list for
#   upstream-ADDED files (umac_datapath_sta.c, umac/relay/*, umac/health_check/*, coredump.c,
#   firmware_mbin.c, …) and upstream-DELETED files (driver/health/driver_health.c, …).
# resolve conflicts -> compile-verify -> grep must-survive -> commit -> tag <ver>-esp32-1

CMakeLists source-list sync is a first-class step

New upstream .c files won't build (and their symbols won't link) until added to the right components/*/CMakeLists.txt; deleted ones must be removed. Compile-verify (link stage) is the safety net that catches a missed sync.

6 · Compile-verify & the fw parity footgun

Harness: make build APP=<app> BOARD=proto1-fgh100m (vendored ESP-IDF 5.4.2). Baseline rimba-halow-mesh already builds green on 3c8ded0d. Recommended per-hop verify set (link-covers all feature areas): test-ampdu-cap, test-swccmp, test-ibss, test-twt-sta, rimba-twt-assoc. Apps needing a submodule feature branch are skipped here and re-verified separately.

🐛 fw parity

esp-halow bundles MM6108 fw 1.17.9; the bench standard is 1.17.8 (1.17.9 regresses STA PS ~2×). Before bench, keep ESP + Linux driver on the same version. Confirm what morselib 2.12.3 requires and whether the bench needs a matching driver/fw bump.

10 · Appendix — our 51 changed files (must-survive intent)

The plan closes with a per-file record of what our 51 changed files exist to do, so a forward-port can be checked for intent survival rather than just for compilation. Entries marked [C] are conflict candidates. It spans the full feature set carried across the hops: IBSS (RISK-01), the 802.11s mesh control + data plane, mesh security (SAE/AMPE + host SW-CCMP incl. the bulk-DMA AES-CCM path), A-MPDU + defrag-before-decrypt, mesh+AP concurrency (the gateway), the TWT responder + requester, the 255-STA AP ceiling with PSRAM-backed tables, the monitor/sniffer RX hook, and the protected_syms.txt export of esp_mesh_ccm_selftest.

Why the appendix matters

Compile-verify proves the tree builds. It cannot prove our features survived a 3-way apply — a silently dropped hunk still links. The must-survive list is what the post-apply grep step checks against, and it is why several low-conflict files are still marked silent-drop-risk.
