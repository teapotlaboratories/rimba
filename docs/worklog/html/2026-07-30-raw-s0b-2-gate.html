RAW S0b-2: the gate is passed
the chip's RAW engine arms, and a STA obeys it

Answer the one question the entire AP-side RAW port has been gated on since the recon: does the MM6108 firmware actually act on a RAW schedule authored by the host? The scoping pass established this is decidable on Linux hardware alone — the blob is the same file on both platforms and RAW reaches the chip only as beacon bytes — so a negative here would BLOCK the port with no ESP code written.

✓ Q3a PASS · Q4 PASS

The engine arms from a host-authored beacon, gates the AP's own TX, and a STA parses a received RPS and self-restricts. The golden byte constant was validated on air, byte-identical, in every beacon. The feature is no longer gated on a source-undecidable firmware question — what remains is entirely ESP-host-side.

RSSI −53 dBm (STA→AP) / −57 dBm (AP→STA). RAW pinned explicitly, per the S0b-0 finding that hostapd's defaults emit a different element:

morse_cli -i wlan1 raw -s 20200,2 -a 1,255 -t 0 enable 1
morse_cli -i wlan1 raw enable 0

Driver readback (passive debugfs dump_raw_configs) confirmed it landed exactly:

RAW ID: 1 (enabled: 1)
  start_time_us=0  aid: start=1 end=255
  slot info: x-slot=0 num=2 duration_us=10100

duration_us=10100 is the 20200 total divided by 2 slots — the double-truncation behaviour S0b-0 predicted from source, landing exactly on the golden parameter. morse_cli raw --help also confirmed -t is "Start time for the RAW window from the end of the frame" — the beacon-end reference the analysis method depends on.

2 · Negative control, then the element on air

Negative control — free, from S0b-1's capture

With RAW disabled, all 2222 beacons carried {0, 5, 213, 214, 217, 221, 232} and zero EID-208 elements. So anything at 208 afterwards is attributable to the RAW config, not to something the firmware emits regardless.

IE chain (1 distinct, x236) : [213, 5, 208, 217, 232, 214, 0, 221]
EID-208 element (1 distinct): D0 06 20 40 09 04 E0 1F
golden constant (7.1)       : D0 06 20 40 09 04 E0 1F
BYTE-IDENTICAL              : True

The golden constant is validated on air, closing the last S0b-0 caveat. The RPS sits at position 3, directly after the TIM, matching Linux's S1G long-beacon ordering.

⚠ A method note, because I got it wrong first

My initial parser brute-forced the IE start offset and required the chain to land on the frame end. It matched only 3 of 242 frames and reported varying offsets — which looked exactly like the conditional S1G presence bits being in play, the trap the plan flagged. Both were artefacts: the frames carry a 4-byte trailing FCS, and once that is accounted for and the walk is anchored on EID 213, all 236 frames parse with a constant 15-byte offset. The presence bits were not set. Recorded because a brute-forced offset is exactly how a false "RPS stripped" verdict gets manufactured.

Q3a — PASS. assignments[0] climbing at roughly one per beacon proves the chip parses the RPS out of its own outgoing beacon every TBTT. invalid_assignments = 0 is the direct confirmation the bytes are accepted — the signal that would have caught the EID-66 error had it shipped. And aci_frames_delayed / frame_crosses_slot moving proves the chip actively gates its own transmissions, not merely parses.

Q4 — PASS. The STA's own assignments[] climbed to 2083, so it parses a received RPS; and its own aci_frames_delayed = 239 proves it defers its own uplink. Since neither host stack contains an RPS parser (Linux's raw.c is AP-only), that behaviour is necessarily in the blob — the same blob the ESP runs.

A useful intermediate read

With RAW enabled and beaconing but before any STA associated, the AP already showed Valid: 1516, Invalid: 0 with all Delayed counters at zero. The engine arms on the advertisement alone; the deferral counters only move once there is traffic to defer. A useful diagnostic separation for later stages.

4 · The timing arm was voided — and why that matters

The phase histogram, computed with the S0b-1 method (relative to the observed beacon, never a fitted grid), put only 9.2 % of uplink frames inside the advertised [0, 20200] µs window — against 19.7 % expected if frames were uniform over the beacon interval. Read naively that says worse than no confinement.

✗ It is not admissible

STA netdev TX packets1194
STA MAC-level TX frames1681
uplink data frames in the capture403
capture completeness~34 % — 66 % loss

The parse was sound — tshark independently found exactly 403 frames carrying the STA's TA. The capture is simply missing two-thirds of the traffic. Per confound row (g) the run is voided, and no confinement conclusion may be drawn in either direction.

This is the finding. S0b-1 measured 2.5 % beacon loss and explicitly flagged, as an untested caveat, that data frames might be lost at a different rate. They are — at 66 %, a 26× difference. So S0b-1's calibration does not transfer to data frames, and any future timing measurement must reconcile data-frame counts against the transmitter's TX counters before a phase histogram is computed. Beacon-count reconciliation is not sufficient.

It does not weaken the verdict: the counters were designated the primary instrument precisely because they are immune to capture loss, and they are unambiguous.

5 · Two things worth carrying forward

  • frame_crosses_slot = 27 on both ends — real frames are too long for a 10100 µs slot at 1 MHz. Combined with the ≤6-slot cap S0b-0 found, this constrains any real RAW schedule: at most 6 slots, and a slot must be long enough to hold a frame at the operating MCS or the frame is deferred rather than fitted.
  • The AP defers its own downlink too (aci_frames_delayed = 92). For the mesh-gate use case, where the gate is already the throughput bottleneck, RAW is not free. The throughput A/B is now clearly worth doing before committing to the port.

6 · Verification status

  • On hardware, on air, three radios. All measurements from live firmware counters and a live capture.
  • On-air frame verification: gold standard reached for the RPS element. Captured on chronium's morse0 from a live Linux device and byte-diffed against the derived constant — 236/236 identical, with a negative control from the RAW-disabled baseline. That is the reference-side frame; the ESP's own RPS remains unverified and that obligation is still owed at S0b-4.
  • Bench returned to radio silence — RAW disabled + deleted, both daemons killed, addresses flushed, morse0 and wlan1 down, type managed restored on all three nodes. Verified with ps -eo comm= rather than pgrep -f, which self-matches. No ESP board was involved.

7 · Caveats

  • This says nothing about the ESP host path. Q2 and Q3b are untouched and need ESP code.
  • Confinement is not demonstrated, only deferral. The counters prove frames were delayed because of RAW; they do not prove the resulting transmissions land inside the window. The measurement that would show that was voided. The mechanism engages, but its on-air effect is not yet characterised — this distinction should not be glossed.
  • One STA, one AID, one assignment, one session. The A/B-1 two-STA disjoint-slot design — the internally-controlled experiment the plan calls the discriminating one — was not run.
  • The AP-side aci_frames_delayed = 92 is small relative to the STA's 239; not investigated.
  • Load was a ping flood, not a rate-controlled generator (neither Pi Zero has iperf3), and it saturated the link, so the offered rate is not precisely known.
