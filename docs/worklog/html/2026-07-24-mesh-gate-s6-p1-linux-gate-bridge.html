S6 P1 (Case A) · the wildcard: can the morse mesh vif even be bridged?

S6 is the last mesh-gate stage — live-Linux interop. P1 is its wildcard: build the Linux-side L2 bridge (mesh vif ↔ a DS segment) that lets an ESP mesh node reach an off-mesh host through a Linux gate. It had never been done on this bench, and the load-bearing unknown was whether the morse driver even permits bridging the 802.11s mesh interface. It does — and the datapath runs clean.

The Linux gate's mpp table learned the ESP-proxied source from the ESP's on-wire AE frames — so the ESP↔Linux mesh-gate datapath is compatible on the wire, not just ESP↔ESP.

The wildcard, answered: the morse mesh vif IS bridgeable

It works — with a specific, non-obvious recipe. Each clause cost a failed attempt:

  1. Interface TYPE matters. Enslaving wlan1 while type managed is rejected (Device does not allow enslaving to a bridge — the classic can't-bridge-a-wifi-station rule). Set it to type mesh point first — a mesh vif is bridgeable (the kernel mpp_path_add learns DS hosts from bridge-forwarded frames; that is the basis of 802.11s gateway support).
  2. Enslave-FIRST, while DOWN. You cannot enslave once the mesh is UP. So: down → set type mesh → master mesh-br → then start wpa_supplicant_s1g. The bridge membership survives the join.
  3. Warm the radio first. A cold bridged join fails at the channel set (morse_cmd_vendor_set_channel … rc -32768). Bring a bare mesh up once (tunes ch27), tear the daemon down, then enslave-first — the re-set of the tuned channel succeeds.
  4. veth must be DOWN to enslave. ip link set ds0 master mesh-br returns rc=0 but silently no-ops if ds0 is UP. Down → master → up. (ip -d link show ds0 showing no master despite rc=0 is the tell.)

The proof, on the gate

$ iw dev wlan1 mpp dump
DEST ADDR         PROXY NODE        IFACE
e2:72:a1:f8:f0:08 e2:72:a1:f8:f0:08 wlan1   # the ESP-proxied source, learned by Linux mpp_path_add

The Linux gate parsed the ESP's on-wire AE frames (mesh.c / mesh_pathtbl.c:722) correctly — the exact proof S6 P1 asked for.

Bench reality: chronite wedged, chronogen the fallback

⚠ chronite dropped mid-test — needs a power-cycle

The plan named chronite as the gate. It set up fine and the ESP peered — but ~2–3 min into bridged-mesh operation its management WiFi (wlan0) dropped (No route to host; chronium on the same AP stayed up, so chronite-specific) and did not recover in 4.5 min. Its MM6108 mesh radio stayed up (still a peer), so only the Pi's management link died — can't ssh in to reload the driver. It needs a physical power-cycle (no remote power control on the bench); that also recovers it and silences its lingering mesh radio.

Pivoted to chronogen (the plan's documented fallback, a Pi Zero 2 W). Bare mesh worked at once; the bridged mesh needed the warm-radio + veth-down gotchas. Once set up, the datapath was rock solid — so a Pi Zero can serve as the bridged Linux gate for a low-rate test.

ESP-side change

firmware/test-mesh-gate-node gained a TEST_MESH_ID override (#ifndef default "rimba-mesh" + a CMakeLists forward), mirroring test-mesh-gate-rx/test-mesh-ae. Its NO_PING responder can now join rimba-smesh to be the far mesh endpoint reached through a live Linux gate (make flash APP=test-mesh-gate-node MESH_ID=rimba-smesh NO_PING=1 → static 10.9.9.108). Fixture-only, split-rule compliant, no morselib change. Re-usable fact: the mesh SAE password rimbamesh2026 is compiled into morselib and identical across rimba-mesh/rimba-smesh, so a MESH_ID= override is all that is needed to point a fixture at a live Linux gate.
