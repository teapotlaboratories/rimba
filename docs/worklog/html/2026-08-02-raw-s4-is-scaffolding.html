RAW S4 — the stage is misconceived
the AID list has exactly one consumer, and it is two stages away · S3 was the finish line

S4 was to build the ordered connected-AID list from the ESP’s dense-AID allocator and map the configured start_aid/end_aid onto the live range. It was written down as the MVP finish line. Reading the code that consumes that list shows the stage does nothing on the MVP path: every use of raw->aid_list sits behind a beacon-spreading guard, and a plain GENERIC RAW — the whole MVP scope — takes the branch that goes straight to the configured range. S4 is dropped. No code was written. The AID-list work moves to S6, where it is actually load-bearing.

✗ This is a cancellation, not a failure

Nothing broke, nothing regressed, no bench time was spent. The stage was read out of the reference before it was implemented, and the reference says — in its own comment — that it deliberately does the opposite of what the plan assumed. The cost of the mistake is a paragraph in five documents; had it been caught after the code existed, it would have been a module, its refresh hooks, and a test with nothing to assert against.

1 · What S4 was supposed to be

From the design doc §3, verbatim:

Design doc §3 — the stage as planned

S4 — AID-list + single-group mapping. Build the ordered connected-AID list from the ESP dense-AID allocator/bitmap … Map config start_aid/end_aid to the live range; refresh on STA join/leave … This is the MVP finish line.

The stated motivation, carried through several worklogs including my own, was that “the advertised group is a well-formed fiction that mostly names AIDs nobody holds” — advertise 1–255 while three STAs are connected, and the schedule doesn’t describe reality. Narrowing the advertised group to the stations that actually exist sounds like an obvious defect fix.

2 · Why it is wrong — the list’s only consumer is beacon spreading

The connected-AID list does not narrow the advertised group. Every use of raw->aid_list, and of start_aid_idx / end_aid_idx, sits behind a beacon-spreading guard:

The decisive evidence is the reference’s own comment

The non-spreading path is not an accident of the port’s reading — the driver says what it is doing, at raw.c:595-599:

    /* If not using beacon spreading or no connected STAs use the full AID range. */
} else {
    current_beacon_start_aid = config->start_aid;
    current_beacon_end_aid   = config->end_aid;
    config->beacon_spreading.last_aid = config->end_aid;
}

return morse_raw_generate_assignment_with_aid_range(mors_vif, config, rps_ie_start,
    current_beacon_start_aid, current_beacon_end_aid);

🐛 “or no connected STAs use the full AID range”

That clause is the whole argument. The reference explicitly handles the case S4 existed to fix — no connected STAs — and its answer is advertise the full configured range anyway. morse_raw_generate_assignment_with_aid_range() is the function S1 already ported, and it receives the configured range. For a plain GENERIC RAW the advertised group is the configured one, and the ESP already emits exactly that.

So building morse_generate_aid_list() plus join/leave refresh hooks now would be dead scaffolding: no on-air change, nothing to verify it against, and its only consumer two stages away.

4 · What this changes

  • S3 is the MVP finish line, not S4. After S3 the ESP advertises a correct, configurable RAW schedule and the chip arms and gates on it. There is no further stage needed to make it work.
  • The AID-list work moves into S6, alongside beacon spreading and PRAW cadence, where it is load-bearing rather than dead.
  • S5 (per-priority AID grouping, multiple assignments per element) is unaffected and remains a real feature.

5 · What I got wrong, and why it survived this long

“S4 is the MVP finish line” went into the backlog, the code map, two worklogs and a PR description before anyone read the code that consumes the AID list. The design doc said it, and it sounded right — an advertisement naming absent stations is an obvious-looking defect. It took about twenty minutes of grepping raw.c to find that the reference deliberately does the opposite, and says so in a comment.

⚠ The same pattern produced the break-even analysis two days ago

A plausible framing carried forward through several documents before anyone checked it against the source — there, the “22 % cost” that turned out to be a Linux-AP number with no ESP A/B behind it. Cheap to catch by reading first; expensive to catch after the code exists.

6 · Where the port now stands

Every firmware question is answered and the implementation works:

S4 ✗ dropped — misconceived AID list has one consumer and it is beacon spreading; work moves to S6
S5, S6 not started real features — per-priority grouping; beacon spreading + PRAW cadence

⚠ The open question is unchanged, and it is not a firmware one

The break-even analysis of 2026-07-31 still says RAW’s payoff cannot be demonstrated: the ~22 % cost figure is a Linux-AP number, and the gateway caps at 8 clients today for reasons unrelated to contention. S5 and S6 are genuine work, but nothing has moved the case for doing them.

✓ Recommendation — stop here

The port has reached a natural, working, documented stopping point. Resume at S5/S6 only if the traffic-mix question or a raised client ceiling changes the economics.

No radios were used and no code was written for this stage.
