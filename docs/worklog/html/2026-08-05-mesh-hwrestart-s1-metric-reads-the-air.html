The fixture that passed a deaf node

S1 of the mesh hw_restart work was blocked by its own success: the reproducer returned PASS on a node that had stopped transmitting entirely. The trigger turned out to be fine. The metric was reading the wrong radio — in fact, it was reading no radio at all.

1 · Two hypotheses, one cheap probe

The previous session left the fixture reporting estab_peers=1 both before and after a forced chip restart, with two readings the output could not separate:

  1. the restart ran and the host peer table is merely stale — the metric is wrong; or
  2. mmwlan_force_hw_restart() returned SUCCESS but the queued event never executed — the hook is wrong.

The decisive probe was already sitting inside the handler: umac_stats' hw-restart counter, which hw_restart_evt_handler() bumps after mmdrv_deinit() and mmdrv_init() have both run. It is reachable from an app through the public mmwlan_get_umac_stats(), so nothing new had to be added to morselib to read it.

TEST|INFO|hw_restart_counter=0 before the trigger
TEST|STEP|restart-ran|PASS|hw_restart_counter 0 -> 1

Hypothesis 2 is dead

The hook added last session is correct — the handler really does execute through the teardown and re-init. Everything that was wrong lived in the metric.

Running this first was worth the ordering. Going straight to the on-air probe would have produced a red result that was ambiguous between “the mesh cannot recover” and “my trigger never fired” — and the same counter read would have been needed anyway, with a far more expensive experiment already built on top of it.

2 · Why no on-device probe can score this

mmwlan_mesh_peer_count() walks mesh_peers[], a host-side array. mmdrv_deinit()/mmdrv_init() tears down the chip and never touches it, so it reads 1 whether the node is meshing or transmitting nothing at all. It held at 1 for the full 45 s window while the monitor saw the board emit zero frames.

The trap is structural, not an oversight

“Silently deaf” is by definition the state in which every host-side view still looks healthy. So any replacement metric that reads RAM on the node under test walks into it again.

The first version picked the peer table specifically to dodge the documented ping/empty-mpath trap, and landed somewhere strictly worse. A fixture that certifies a broken node as healthy is worse than no fixture — it spends credibility instead of building it.

This is not a new pattern here — it is the test-raw-rps shape, whose TEST| gates are also preconditions with the real verdict decoded from a capture. The firmware still prints mmwlan_mesh_peer_count(), demoted to INFO and explicitly labelled unscored, so the stale number stays visible next to the on-air truth. That contrast is the finding; deleting it would hide the lesson.

4 · The measurement

The scorer reads morse0 over AF_PACKET, filters S1G beacons by source address, and scores the shape beacons → gap → beacons? — so it needs no clock sync with the device under test.

captured 150s: nut=317 beacons, peer(control)=1367 beacons
nut beacon window: first=+0.0s last=+37.9s  (trailing silence 112.1s)
control rate: 9.1/s before the node went quiet, 9.1/s during its silence
RESULT|FAIL|the node's beacons stopped at +37.9s and NEVER returned ...
NUT, before~9/s
NUT, after0/s
control, before9.1/s
control, after9.1/s

The liveness control is what makes this a measurement

The peer board is unaffected by the restart and beacons throughout. Its rate holding steady across the node’s silence is what proves the monitor still had the channel — so zero NUT beacons is silence and not a capture that quietly died. Without it, “no beacons” would be unfalsifiable: the same absence-of-evidence mistake that produced the original bad PASS, wearing a different costume. The tool reports INCONCLUSIVE rather than FAIL when the control drops, for exactly that reason.

The PASS branch is not dead code

A scorer that has only ever emitted FAIL is not yet a scorer. Validated by rebooting a plain mesh node mid-capture and pointing the tool at it:

nut beacon window: first=+0.0s last=+75.0s  (trailing silence 0.0s)
  gap 4.9s  (+20.0s -> +24.9s)
RESULT|PASS|the node's beacons stopped for 4.9s and RESUMED at +24.9s (469 beacons since)

Both branches now fire on real air, so the FAIL above is a finding rather than a tool stuck on one answer.

5 · Dead ends and bench notes

  • The first run of the day was lost. I piped the serial capture through grep, and the capture script died on ModuleNotFoundError: No module named 'serial' — the traceback went into the same grep and vanished. pyserial lives in the IDF venv, not system python3. The app parks forever after TEST|END, so the verdict was unrecoverable. Same family as the documented “never pipe a tier through tail” footgun.
  • morse0 will not come up until wlan1 is up and tuned. tcpdump failed with “That device is not up”: the driver forwards to morse0 only while monitor_mode is true, which needs a live monitor-type vif. Order is wlan1 up → set freq 5560 → morse0 up, and it must be re-verified with ip -br link rather than assumed from the absence of an error.
  • tcpdump cannot decode S1G beacons — they print as “unknown 802.11 frame type (3)”, an S1G beacon being a type-3 (extension) frame. Parse the bytes: SA at frame offset [4:10], fc == 0x1c.
