1 · The design changed before a line was written

The backlog framing was “add umac_mesh_handle_hw_restarted(), mirroring the connection one, looping over N peers instead of one BSSID”. Reading ieee80211_reconfig() (util.c:1753) first said otherwise.

Linux’s mesh case is three lines — re-enable the beacon — because everything a mesh vif needs restored happens generically, before the type switch: drv_add_interface(), ieee80211_reconfig_stations(), ieee80211_reenable_keys().

The root cause, stated properly

morselib put that same generic work inside umac_connection_handle_hw_restarted(), a STA-only function keyed on UMAC_INTERFACE_STA. A mesh node gets nothing not because a mesh handler is missing, but because the generic restore was written into a STA-specific function.

A reading trap I fell into for several minutes

ieee80211_reconfig has two switches on vif.type. The first (station re-add) has no MESH_POINT label, so mesh takes its default: arm and is re-added; the MESH_POINT case at util.c:2043 belongs to the second switch and only touches beaconing. Conflating them yields “Linux never restores mesh peers” — the opposite of the truth.

3 · The part worth reading: “it works” was wrong twice

First “it works” — beacons only

The S1 scorer went green: beacons stopped 2.94 s at the trigger, then ran for 140 s. Against a pre-S2 baseline of 112 s of silence and never returning, that looked conclusive, and I said so. It wasn’t.

190 s of continuous beaconing, and 0/5 pings

Beaconing proves the vif is on air. It proves nothing about the datapath. The fixture gained a ping — before and after, the before-ping being what makes the after-ping readable, since a bare post-restart failure is ambiguous with “this rig never carried traffic”. The node had answered 5/5 a minute earlier: perfect on air, dead as a network node.

Defect 1 — the common stad’s keys were never replayed

umac_mesh_install_common_keys() runs at start, and its own comment says it plainly: “The common_stad drives ALL mesh TX (every mesh frame dequeues from it).” Recovery never re-pushed them. Beacons are host-generated and unencrypted, so they sailed through while every data frame died — invisible in a beacon capture by construction, which is exactly why the on-air metric S1 was built around could not see it.

Defect 2 — I was resetting our CCMP packet number to zero

Fixing defect 1 changed nothing: still 0/5. Every command returned success. Nothing logged an error.

The fix is to stop rebuilding keys at all. Only the chip lost its copy; the host keychain survived intact, PN and all. umac_keys_reinstall_keys() re-pushes that existing chain without touching the counters — the same primitive the STA path already uses (umac_connection.c:1721) and the same intent as ieee80211_reenable_keys().

The bug was a divergence from the reference; the fix was to stop diverging

Linux re-enables existing key objects. I had invented a rebuild. The porting rule earns its keep here not as paperwork, but because the reference’s shape encoded a constraint I didn’t know existed.

Defect 3 — my own scorer’s PASS was structurally unsound

It required a gap to award PASS. So a recovery too fast to drop GAP_S worth of beacons was reported INCONCLUSIVE — better behaviour, worse verdict — and when an unrelated gap (the board’s own reboot) shared the capture, PASS was awarded keyed on that. Right answer, wrong evidence: the exact failure the tool exists to prevent, reproduced inside the tool. The verdict now rests on a solid baseline plus beacons still flowing at the end, with the gap as diagnostic detail. GAP_S also dropped 3.0 → 2.0 s, since the measured teardown outage is 2.94 s — the old threshold sat just above the thing it was meant to catch.

5 · The adversarial review — which refuted three of my own claims

Having declared the port Linux-faithful, I ran a pass whose goal was to refute that. It did, three times, and the most important finding is that I had violated my own stated design.

R1 — I wrote “a hoist, not a mirror”, then shipped a mirror

umac_connection_handle_hw_restarted()’s STA guard spans umac_connection.c:1697-1797, and inside it sat the fragmentation threshold restore — value from umacd config, pushed via mmdrv_set_frag_threshold(), which takes no vif. It is hw-global, Linux restores it unconditionally at util.c:1836, and a mesh node never entered the body that restored it. I diagnosed exactly this bug class as the root cause, prescribed a hoist, then added a parallel mesh function that left it stranded. Now hoisted into hw_restart_evt_handler(). Latent rather than active — no app sets a frag threshold — but a future one would have lost it silently.

  • R2 — D7 was factually wrong. I wrote that morselib has “no conf_tx/EDCA surface at all”. It does: umac_connection.c:911-951 builds aifs/cw_min/cw_max. My grep was too narrow. The conclusion survives — that plumbing is fed by an AP’s EDCA element a mesh node never receives — but a code map that misstates the reference is worse than one that omits the row.
  • R3 — D3 cited a constraint that doesn’t apply. I justified keys-before-beaconing with the host-beacon-engine ordering; that is a start-path constraint, and in recovery mesh_ctx is already populated. Both references do beacon-then-keys. The ordering is a deliberate choice — live peers resume the instant we are back on air, so keys-first closes a window where we advertise presence with no crypto — now recorded as a choice, not a constraint.
  • R4 — D8 survived. The plink tick is a umac_core timeout, cancelled only in mmwlan_mesh_stop(); mmdrv_deinit/init does not touch it.

And the hoist broke a build I had never been building

Adding the hoist, I built rimba-halow-sta for the first time and it failed to link: undefined reference to umac_ap_get_beacon. Bisected, not guessed.

An undefined symbol surviving on an accident of dead-code elimination

mmdrv_host_get_beacon() calls umac_ap_get_beacon() unguarded, while umac_ap.c is not compiled when CONFIG_HALOW_AP_MODE=n. That build only ever linked because --gc-sections dropped the whole dispatcher when nothing referenced it. My mesh recovery call pulled umac_mesh.o, and with it the dispatcher, back into the link. Fixed with the MMWLAN_AP_DISABLED guard the tree already uses.

The lesson is narrower than “build everything”: a change to a shared shim can retain code that was previously collected, so its blast radius is every build configuration, not the one you are testing.

Re-verified on hardware after all of it: datapath 5/5 before, 5/5 after; beacons 1705 over 190 s, longest interruption 3.0 s. Four configurations clean-build.

6 · The code review — two bugs concealing each other

A /code-review pass returned eight findings. All eight were real. The first invalidated a claim I had repeated since the original investigation, and fixing it uncovered a worse defect of my own.

The premise was wrong, and had been all along

I had written — in the design doc, the worklog, the commit message and the shim comment — that umac_connection_handle_hw_restarted() “skips its whole body on a mesh node”. It does not: UMAC_INTERFACE_STA is inside VIF_STA_INTERFACE_TYPES_MASK, so the lookup returns the STA-slot id without consulting active_interface_types — and mesh shares that slot. Settled on hardware, not by re-reading:

E 31250 ev umac_connection_handle_hw_restarted[1699] PROBE: BODY RUNNING vif_id=0

So both handlers had been running, the connection one re-running umac_interface_reinstall_vif() right after the mesh restore finished.

That fix broke recovery — and the reason is the real find

With exclusivity enforced: 0/5 pings. I bisected rather than guessed. It was the channel.

Two bugs concealing each other

The mesh restore had never restored the channel. It passed every earlier bench run only because the un-enforced double dispatch meant the connection handler re-did the channel afterwards. A redundant call I thought was harmless was in fact load-bearing, for a step I thought I had implemented. Removing one exposed the other. mesh_chip_configure_bss() now does not touch the channel at all, so the choice cannot be made by accident.

7 · Found and deliberately NOT fixed

mmwlan_mesh_start() pushes an all-zero BSSID to the firmware

It calls umac_interface_get_vif_mac_addr(umacd, vif_id, mesh_mac) — passing a uint16_t driver vif id into an enum mmwlan_vif parameter. The mesh vif id is 0; MMWLAN_VIF_STA is 1 and MMWLAN_VIF_UNSPECIFIED is 0, so it resolves to UNSPECIFIED, umac_data_get_interface_vif() returns NULL, the function returns MMWLAN_UNAVAILABLE without writing, the return is discarded with (void), and mmdrv_set_bssid() receives six zero bytes.

Same shape as the proxy-ARP defect: a malformed field nobody reads. Left alone on purpose — an unrelated change to shipped mesh start behaviour that could plausibly alter firmware RX filtering and needs its own A/B. Bundling it would have confounded this session’s result: if peering had regressed I could not have told which change did it. Needs filing.

8 · Bench notes

  • The scratchpad was cleared mid-session, so the serial runner vanished; I piped its No such file error into a grep and got a silent empty run. Second time this session for that family of mistake. The rule is not so much “don’t pipe through grep” as never let a run’s stderr go somewhere you aren’t reading.
  • MMLOG_DBG/MMLOG_INF do not reach the UART; only MMLOG_ERR does. Diagnosing the recovery meant temporarily elevating the per-peer logs, then reverting. Worth knowing before assuming a code path didn’t run.
