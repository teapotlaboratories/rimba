An AP arm — and the dispatch that had no room for the gateway

The MMOSAL_ASSERT(false) that panicked a mesh + AP node on a hardware restart is gone, and the AP host-slot has a real restore arm. The blocker was never a missing branch: it was that morselib had collapsed Linux’s loop over interfaces into a single either/or.

1 · The blocker, and why a third branch was the wrong shape

The handover said the dispatch had “no room for the gate’s mesh + AP case” and needed revisiting, not extending. That is right, and the reason is in the reference.

ieee80211_reconfig() does not choose an interface type

It loops over interfaces — net/mac80211/util.c:1902, list_for_each_entry(sdata, &local->interfaces, list) — and each one independently takes its own arm of the type switch. A Linux mesh gateway is two sdata entries and both are walked. morselib had collapsed that loop into one either/or, which is precisely the construct that cannot express “both”.

morselib has exactly two host slots (VIF_STA_INTERFACE_TYPES_MASK, umac_interface.c:118-120), so the restore goes per slot, not per type:

Two arms, not three

The exclusivity S2 fought to enforce is real, but it lives within the STA slot, not across the radio. Conflating those two is what made the gateway look unrepresentable.

The #if around the AP call is load-bearing

umac_ap.c is not compiled when CONFIG_HALOW_AP_MODE=n (components/morselib/CMakeLists.txt:120 defines MMWLAN_AP_DISABLED=1), so an unguarded reference is an undefined symbol at link. Same trap already documented on umac_mmdrv_get_beacon(), which the S2 work tripped once by pulling umac_mesh.o back into a build that had been getting away with --gc-sections. Verified by building test-idle: links clean.

2 · The channel moved — and a second caller nearly made that silent

With two slots restoring, umac_interface_reconfigure_channel() could not stay inside the arms: on the gateway the AP arm would have programmed the channel a second time, after the mesh arm had already armed beaconing. One radio, one channel, one restore.

It is genuinely HW-global, which is what licenses the hoist: mmdrv_set_channel() is issued with MMDRV_VIF_ID_INVALID (driver/driver.c:864), as are the txpower, duty-cycle and mpsw commands beside it (umac_interface.c:834-866). Linux puts ieee80211_hw_config() in the same place — once, before the per-vif loop.

The trap, caught before it shipped

umac_connection_handle_hw_restarted() has a second caller that never passes through the restart handler: wnm_sleep_fsm_active_exit() (umac_wnm_sleep.c:281-286) re-inits the chip after a WNM chip-powerdown and drives the connection restore directly. Removing the channel call from that function would have silently dropped the channel restore on the power-save wake path — a path this bench cannot easily exercise. So the connection arm keeps its own copy. The cost is one redundant SET_CHANNEL with the same value on a STA restart, before any vif is beaconing, and both files carry the reason inline so a later reader does not tidy the “duplicate” away.

Fourth instance of the same host-cache trap

It must be reconfigure_channel(), never set_channel_from_regdb(): ie_s1g_operation_is_equal() against current_s1g_operation short-circuits, programs nothing, and returns SUCCESS. Joins the channel cache, the CCMP PN counters and pwr_mode on that list.

3 · What the AP arm does

5umac_keys_reinstall_keys() for sta_common and each STA, plus the seq-number spacesieee80211_reenable_keys() — util.c:2108

AP stations are re-added AFTER the beacon, not with everyone else

Linux’s first switch has case NL80211_IFTYPE_AP: carrying the comment “AP stations are handled later” and deliberately does not fall into ieee80211_reconfig_stations(). Copying the mesh arm’s ordering here would have diverged from the reference for no reason.

Two S2 lessons that apply unchanged to the AP

  • Re-push keys, never rebuild them. connection_keys_install_key() copies tx_seq/rx_seq out of the struct it is handed (connection_keys.c:118-121), so a freshly built key rewinds this node’s CCMP PN to 0 while the associated STAs — which did not restart — keep their replay windows. Every install returns success and nothing is logged.
  • sta_common is not optional. It carries the group keys. Skipping it gives an AP that beacons and answers unicast while every group-addressed frame dies — the AP-side twin of the mesh common_stad defect S2 found only after a beacon-only capture had looked green.

Abort is deliberately not umac_ap_disable_ap(). That path is written for an app-initiated shutdown and is unsafe from inside the restart event loop: it issues mmdrv_stop_beaconing() at a chip that just failed a command, tears down the hostapd interface, and sleeps 100 ms. umac_ap_abort_restore() instead reports MMWLAN_LINK_DOWN through the vif-state callback and leaves the allocation intact so a later mmwlan_ap_disable() still works. The asymmetry with umac_mesh_abort_restore(), which does tear down, is justified: a half-restored mesh leaves self-rescheduling plink/RANN timers armed and every peer stad leaked. The AP has neither.

Not restored, stated rather than hidden: AP-side TWT responder agreements. The responder itself is re-armed by umac_interface_init_vif(), but per-STA agreements the chip held are gone and there is no responder-side equivalent of umac_twt_install_pending_agreements(). Tracked separately.

The control never gapped, so both silences are the node’s and both recoveries are real.

The AP recovering 2.9 s faster than the mesh had to be explained before the PASS was worth anything

The AP arm runs after the mesh arm, so it should be slower. It is not a paradox: the mesh’s first beacon lags its arming. The same ordering appears on a plain cold boot in the same capture — AP back after 3.67 s, mesh after 5.00 s — where the mesh is started first. So the lag belongs to the mesh beacon engine, not to the restore. Consistent with mesh_chip_start_beaconing logging config_beacon_timer fw_status=14 and falling back to MESH_CONFIG to arm beaconing.

Measured incidentally: with an AP vif sharing the radio the node’s mesh beacon rate drops to 6.3/s (S2 measured 8.25/s mesh-only) while its AP beacons run at 9.1/s — ~15.4 beacons/s total off one radio. Airtime sharing, not a regression, but worth knowing before reading a mesh beacon count off a gateway.

The bench inventory’s MACs are derived, and wrong

docs/reference/rimba-bench-devices.md lists board2’s mesh MAC as e2:72:a1:f8:f0:08, derived from its efuse MAC. Its actual HaLow MAC is bc:2a:33:96:b2:33 — the MM6108 module has its own MAC and it is not the ESP efuse MAC ± a bit. Deriving the AP BSSID that way would have pointed the scorer at an address nothing transmits. The fixture now reads it back with mmwlan_ap_get_bssid() and prints it.

5 · The client run — what it proved, and what it did not

board2 ran test-apsta-sta and associated to the NUT’s AP over SAE. Its pings fail by construction — the hwrestart fixture has no AP-side netif and pins all TX to the mesh vif — so the client is an association, not a datapath. Timeline anchored on the AP beacon gap at pcap +38.0 → +39.1:

pcap tevent
+38.0chip restart; AP beacons stop (mesh stops +38.1)
+39.09client → AP deauth — 1.1 s into the outage, while the AP is still off air
+39.1 / +41.2AP / mesh beacons resume
+43.47AP → client probe response — the AP’s management path is alive
+44.92client → AP auth ×5, unanswered
+49.91client → AP deauth ×5
+59.11 → +60.62probe-resp, auth both ways, assoc-req/resp — client re-associated

The client’s link did not survive, and it is worth being precise about why that is not evidence against the restore:

  • It gave up 1.1 s into the outage, before the AP had finished coming back. No AP-side restore can prevent that; a chip restart is 1–4 s of silence and this STA’s tolerance is shorter.
  • The AP was answering probe requests 5 s after the restart, so its management path recovered. The 15 s during which it ignored the client’s auths is consistent with 802.11w SA-Query / association-comeback on a PMF-required BSS whose hostapd still believed that STA associated — which is what a successful station restore looks like from outside.
  • No AP: … FAILED or AP: hw-restart restore ABORTED appeared. Every failure path in the new arm is MMLOG_ERR, and MMLOG_ERR demonstrably reaches this UART.

Stated plainly: steps 4 and 5 are NOT directly verified

The per-STA ladder, the per-STA keys and the group keys are inferred from the three points above. The concrete blocker: no client on this bench tolerates a multi-second AP outage, so the restored station entry is made moot by the client’s own deauth before anything can be sent over it. Closing it needs either a client with a longer beacon-loss tolerance, or the trigger wired into test-mesh-ap-gate — which has a working AP-side datapath and IP forwarding — so a ping across the AP link can be scored before and after. That is the right next step for the AP side and is deliberately not being claimed here.

An attempt to get direct evidence by rebuilding at MMLOG_LEVEL_INF, to capture the arm’s own AP: restored vif %u with %d associated STA(s) summary, failed to link: undefined reference to 'mm_hexdump' from umac_datapath.c. A pre-existing morselib gap at INF level, unrelated to this change; the temporary edit was reverted.

6 · The scorer now reads two addresses

tools/mesh_hwrestart_cap.py gained --ap <bssid>, and the per-phase logic moved into a score() function run once per address. One design point matters.

“Did a restart happen at all?” is evidence about the radio, not about one vif

The gapless-capture INCONCLUSIVE branch — which exists because every early-exit in the fixture parks before triggering a restart, so a mis-rigged run would otherwise score PASS — now consults restart_observed, computed across every scored address. Keyed per-SA it would have called this very run’s AP arm INCONCLUSIVE: the AP’s 0.98 s outage is under the 2.0 s threshold while the mesh’s 3.88 s is plainly a restart. Single-address behaviour is unchanged, because with one SA the global test reduces to the local one.

INCONCLUSIVE dominates FAIL in the combined verdict: a capture that does not contain the trigger cannot condemn anything in it.

8 · Stage 1b — closing the gap, same day

Section 5 ended with steps 4 and 5 inferred rather than measured. The restart trigger then went into test-mesh-ap-gate, behind HW_RESTART=1 — the one fixture with a real AP-side datapath (a second esp_netif on 192.168.12.1, per-vif RX demux, per-vif TX tagging). Two probes, because one of them cannot work on this bench.

probescoresneeds the client to survive?
A — group-key PN continuity, off airstep 5’s group halfno — the AP owns the GTK alone
B — unicast ping across the AP linkstep 4 + step 5’s pairwise halfyes

Probe A — PASS, and it is a direct measurement of the S2 defect

The gate emits a 5 Hz broadcast train on its AP subnet. Those frames are group-addressed, so the AP encrypts them with the GTK on sta_common — exactly the keychain step 5 re-pushes — and the CCMP packet number sits in the clear in every header.

marker boundary: last 100B frame at +43.93s, first 114B frame at +45.01s  ->  outage 1.08s
PN across it: 135 -> 136  (delta +1)   key id 1 -> 1
control beacon rate: 8.5/s before the outage, 8.9/s after
RESULT|PASS|the AP's group key SURVIVED the restart

The PN advanced by exactly +1 on an unchanged key id, across a 1.08 s outage that matches the 0.98 s AP beacon outage from stage 1. The group key was re-pushed, not rebuilt. Had it been rebuilt, every associated station would have discarded every group frame as a replay — silently, with every install returning success.

The capture contains its own positive control

Two legitimate PN resets sit in the same window: at +7.09 s (the AP booting) and +17.11 s (the first client’s association triggering a GTK install), both PN → 1. They are what make the negative result mean anything — the instrument demonstrably can see a rewind, so not seeing one is evidence rather than absence of evidence. The tool reports them instead of filtering them, and warns when a run contains none.

Probe B — INCONCLUSIVE, and that is the right answer

TEST|STEP|data-before|PASS|5/5 replies from the client across the AP link
TEST|STEP|restart-ran|PASS|hw_restart_counter 0 -> 1
TEST|STEP|data-after|PASS|5/5 replies (was 5/5 before)
TEST|INFO|assoc-churn|1 association event(s) before the restart, 2 after -- the client RE-ASSOCIATED
TEST|RESULT|INCONCLUSIVE|... that ping crossed a FRESH association ...

A 5/5 after-ping that means nothing. Without the association counter this run would have printed a confident PASS on the strength of traffic crossing a link rebuilt from scratch during the outage. The counter earned its place on the first run. What the run does establish is that the AP is fully functional afterwards — it beacons, completes SAE, and carries traffic.

The tool was wrong on its first run, and the bench caught it

Version one located the restart as the largest gap in the train, reusing the idea from the mesh scorer. It returned:

outage: 3.33s at +3.88s -> +7.21s   PN 1379 -> 1
RESULT|FAIL|the AP's group key was REBUILT across the restart ...

That gap is the board’s own reboot, not the chip restart — and a reboot legitimately installs a fresh GTK at PN 1. The reboot’s hole is larger than the restart’s, so “largest gap” picks the wrong event every time. A textbook PASS scored as a FAIL.

The rule this produced: a scorer must LOCATE its event, not recognise it by size

The fixture now switches its broadcast payload to a longer one immediately before triggering — 18 B → 32 B, which is 100 B → 114 B on air — and the tool measures across that boundary. It has to be length because the frames are GTK-encrypted: the sniffer can see how big they are and nothing else. This is the third time on this epic that a verdict keyed on the biggest or last thing in the window turned out to be keyed on whatever else happened to be in the window.

Regression check and build notes

  • test-mesh-ap-gate is a T2 fixture, so changing it means re-running its scenario, not just building it: make test-t2 TEST=mesh-ap → PASS in 391 s, plus the tier’s own radio-silent sweep.
  • The gate overflowed its app partition by 0x2dd0 once the arm pulled in esp_ping and the lwIP socket API. It now carries a 2 MB partitions.csv, applied to both arms because the partition table is chosen at Kconfig time and cannot follow a -D.
  • TEST_HW_RESTART is a CMake cache variable, so the arm is sticky exactly as TEST_AP_VIF is. HW_RESTART=0 or a wiped build directory; omitting it inherits the arm.

What is still unproven — now a measurement, not an inference

Step 4 and the pairwise half of step 5. The blocker is no longer “no client tolerates the outage” read off one capture; it is a scored, repeatable INCONCLUSIVE with the association count as its evidence. Closing it needs a client that holds its association across a 1–4 s AP outage — either exposing morselib’s connection-monitor control through the public API, or a Linux HaLow STA whose tolerance can be configured. Both are larger than this stage, and neither is being claimed.

9 · Review round — four findings, all real

/code-review at high against the submodule PR, before merging. Every finding was verified against the source rather than taken on trust; all four stood up, and one was a genuine correctness bug in code the bench had already passed.

1 · The AP’s sequence-number restore went to the WRONG vif (high)

umac_datapath_handle_hw_restarted() derived its vif from get_vif_id(umacd, UMAC_INTERFACE_STA) — correct for the STA and mesh callers, since mesh shares that host-slot, and silently wrong for an AP one. On the gateway it aimed an AP client’s counters at the mesh vif while leaving the AP vif’s at the post-mmdrv_init() zero — the exact duplicate-detection rewind the call exists to prevent.

This is the same trap S2 documented, walked into from the other side. S2 found that this lookup returns the STA slot without consulting active_interface_types. I recorded that, then reused a helper built on it for an AP stad. The generalisation: any get_vif_id(UMAC_INTERFACE_STA) inside a routine that can be handed an arbitrary stad is a latent bug. vif_id is now a parameter; STA and mesh pass exactly what they resolved before, so their behaviour is bit-identical.

A green run is not proof of everything the code does

Stage 1b passed with that bug present — probe A measures the group key, which has no per-peer sequence spaces, and probe B was already inconclusive for an unrelated reason. Worth remembering before treating a PASS as coverage.

2 · sta_common got a baseline for an all-zero address (medium)

The AP’s sta_common never gets a peer address — only a BSSID, and it is calloc’d. The mesh common stad does carry this node’s own MAC, which is what makes the equivalent mesh call meaningful. I copied the call across without checking the premise held. Dropped, with the asymmetry written where a reader will look for it.

3 · The channel hoist downgraded a fatal error to a log line (medium)

(a) Inside the arms the call had consequences — a mesh abort, or UMAC_FATAL_ERROR() for STA. Hoisted, it only logged, and both arms then re-armed beaconing on a chip whose channel was never programmed. The handler printed “the node will be unable to transmit or receive” and carried on, manufacturing the silently-deaf state this feature exists to eliminate.

(b) Worse, and I had not seen it: umac_interface_reconfigure_channel() memsets the cached S1G operation up front, and set_channel_internal() only rewrites it on a successful set. A failure leaves the cache zeroed — so every later call reads operating_channel_index == 0, takes the empty branch and returns SUCCESS having programmed nothing. One failure permanently disables the retry, silently — including the WNM-wake caller I had deliberately preserved, so the “keep the duplicate for safety” reasoning was protecting a call a single earlier failure would have neutered. Both halves fixed.

4 · A vif alone does not mean the AP started (low)

umac_ap_start()’s failure path frees the config but does not remove the interface it added, so a restart could pass a vif-only guard and push cfg_bss(beacon_interval=0, dtim_period=0) plus beaconing on a dead config. The guard now also requires config.head. The interface that path leaks is a separate defect, called out rather than fixed in passing.
